# تعارض تطبيق Bankai مع تثبيت Elegance — فحص جهاز فعلي

تم الاتصال بجوال Samsung SM-A065F عبر USB وتصحيح Chrome. صفحة Elegance تستخدم HTTPS وmanifest سليمًا ولا يعرض `Page.getInstallabilityErrors` أخطاء. لكن حدث التثبيت غير متاح في الصفحة. صفحة `chrome://webapks` على الجوال أظهرت:

- تطبيق إدارة Bankai sushi مثبت، بهوية `/merchant-app/shops/116`.
- نطاقه المسجل `https://ozman.online/` ورابط تشغيله `/merchant-app/launch/bankai-sushi`.
- تطبيق Elegance غير موجود ضمن WebAPKs المثبتة.

هذا تعارض نطاقات: تطبيق الإدارة المثبت يغطي صفحة تطبيق الزبائن. [Google توثق منع ترويج التثبيت عند وجود تطبيق أوسع مثبّت](https://web.dev/articles/building-multiple-pwas-on-the-same-domain).

## الإصلاح

أصبح نطاق كل تطبيق إدارة `/merchant-app/{slug}/`، وصفحة تثبيته `/merchant-app/{slug}/install` ورابط تشغيله `/merchant-app/{slug}/launch`. الهوية القديمة `/merchant-app/shops/{id}` وملف manifest في عنوانه القديم يبقيان ثابتين حتى يتعرف المتصفح على تحديث التطبيق الموجود. رابط التشغيل القديم ما زال يعمل ويتحقق من الملكية والدخول. `/merchant-app` يختار المحل الحالي ويحوّل لصفحة تثبيته الجديدة. كل الاختصارات داخل النطاق الجديد.

فتح التطبيق يستمر بتحويل صاحب المحل للوحة الإدارة الحالية، مع تطبيق صلاحياتها المعتادة. لأن لوحة الإدارة خارج نطاق نافذة PWA الجديد، قد يعرض Chrome شريط المتصفح عند الانتقال إليها. لا يتم استدعاء متحكمات الإدارة متجاوزًا middleware الصلاحيات. جعل جميع صفحات الإدارة تعمل داخل نطاق مستقل لكل محل يحتاج ترحيل مسارات إدارة منفصلًا.

## النشر والجوال الحالي

ارفع `app/Http/Controllers/MerchantPwaController.php` و`routes/web.php` و`resources/views/front/partials/merchant_pwa_head.blade.php` ثم شغّل `php artisan optimize:clear`. لا توجد migrations. لا يكفي تحديث JavaScript لأن المشكلة في نطاق manifest الخاص بتطبيق الإدارة.

بعد النشر، افتح Bankai ثم `chrome://webapks` واضغط تحديث Bankai، وانتظر تحديث التطبيق وتحقق أن Scope تغيّر إلى `/merchant-app/bankai-sushi/`. تحديث ملف السيرفر وحده لا يغيّر فورًا نطاق WebAPK المثبت. إذا لم يطبّق المتصفح التحديث، يحتاج التطبيق القديم إعادة تثبيت بموافقة المستخدم مع المحافظة على بيانات الموقع؛ لا تمسح بيانات Chrome أو ملفات الحساب.

ثم افتح صفحة تثبيت Elegance في Chrome وجرّب التثبيت. تأكد من وجود Bankai وElegance معًا بنطاقين غير متداخلين.

التحقق المحلي: 28 اختبارًا نجح (903 تأكيدات)، بما فيها استمرار الدخول، رفض فتح مثبت محل آخر، الهوية الثابتة، احتواء روابط التشغيل والتثبيت والاختصارات داخل النطاق، عدم تداخل تطبيق الإدارة مع تطبيقات الزبائن أو إدارة محل آخر، وتوافق رابط التشغيل القديم. يغطي `PwaIsolationTest` عشر محلات من جميع أنواع الكتالوج وعشرين تطبيقًا للزبائن والإدارة، بأسماء مكررة وروابط متشابهة، ويقارن النطاقات في الاتجاهين. يتأكد أيضًا من بقاء هوية التطبيق بعد تغيير الاسم والرابط ومن فتح المحل المطلوب عند التنقل بين تطبيقات عدة مع جلسة صاحب محل مشتركة. هذا فحص لإعدادات التطبيقات واستجابات السيرفر، وليس تثبيت عشرين تطبيقًا فعليًا على الجوال.

تحتاج هذه التغييرات إلى النشر على الموقع وتحديث نطاق التطبيقات المثبتة سابقًا. لم تُحذف تطبيقات الجوال أو بياناته.

في مسار النشر المعتاد لهذا المشروع، بعد Commit وPush شغّل من مجلد المشروع داخل جلسة SSH الموجودة:

```sh
git pull --ff-only origin main
php artisan optimize:clear
```

إذا فشل `git pull` لا تتجاوز الخطأ باستخدام `reset --hard`؛ راجع التغييرات الموجودة على السيرفر أولًا. لا توجد migrations في هذا الإصلاح.

## إكمال التجربة على الجوال

عرض Chrome رسالة «سبق وتم تثبيت هذا التطبيق» عند محاولة تثبيت Elegance مع أن التطبيق غير موجود. عند تعطيل حزمة Bankai مؤقتًا دون حذفها، تغيّر `beforeinstallprompt` من غير متاح إلى متاح وظهرت عبارة «التطبيق جاهز للتثبيت على جهازك». أُعيد تفعيل Bankai مباشرة، ثم استُخدم طلب التثبيت المتاح وثُبّت Elegance من نافذة Chrome الأصلية.

تحقق Android من وجود حزمة Elegance الجديدة `org.chromium.webapk.a4703a0d9079e02eb_v2`، ومن بقاء حزمة Bankai `org.chromium.webapk.adbab3df3176d4593_v2` مفعّلة. فُتح Elegance من نشاط التطبيق المثبّت وظهرت واجهة المحل ومنتجاته بدل شاشة CSS. هذا يحل التثبيت على الجوال الحالي؛ يظل نشر إصلاح نطاق الإدارة وتحديث تطبيق Bankai المثبّت مطلوبين لمنع تكرار التعارض مع محلات أخرى.

## متابعة النشر واكتشاف التحديث

نُشر إصلاح النطاقات `53799ce`، وتحقق فحص ملفات الموقع العامة من 342 manifest تخص 171 محلًا فعالًا، دون تداخل نطاقات أو تكرار هويات. سبع استجابات أعطت HTTP 500 مؤقتًا ثم نجحت عند إعادة المحاولة؛ لا يثبت هذا الفحص خلو الاستضافة من أخطاء عابرة أو تثبيت كل التطبيقات فعليًا.

وجد الفحص اللاحق أن صفحات الإدارة النهائية التي يصلها التطبيق بعد تحويل رابط التشغيل لا تحتوي رابط manifest. أُضيف الرابط فقط لصاحب المحل الفعال في لوحات المطاعم والمحلات والخدمات العقارية، دون إضافة أزرار تثبيت أو طلب أذونات. يتيح ذلك اكتشاف نفس manifest عند فتح التطبيق القديم. يغطي اختبار جديد سلسلة التحويل حتى صفحة الإدارة في الحالات الثلاث؛ فشل قبل الإصلاح ونجح بعده. نتيجة المجموعة: 29 اختبارًا، 912 تأكيدًا.

يجب رفع `resources/views/admin/partials/merchant_app_manifest.blade.php` وملفات اللوحات الثلاث المعدلة أيضًا، ثم مسح كاش Blade بالأمر المعتاد. لا تكفي عبارة Succeeded في `chrome://webapks` وحدها: يجب التحقق من تغير Scope المسجل فعليًا قبل إعلان اكتمال ترحيل التطبيق القديم.
